## 2. 왜 만들었나: 학습과 채용 사이의 단절  _(1:50 누적 · 70초)_

**핵심 시각 자료**: 문제 3카드 → 해결 흐름(수요 분석→진단→갭→Pick)

**본문**

- 학습자: 무엇을 배워야 취업에 유리한지 알 수 없음
- 기업 수요 데이터: 채용공고·공공 고용 통계·AI Hub로 파편화
- 학습 운영: 진도·추천 성과를 감으로 판단
- 해결: 수요 분석 → 역량 진단 → 갭 → 맞춤 Pick → 운영 지표

**발표자 스크립트**

> 출발점은 학습과 채용이 따로 논다는 문제의식이었습니다. 학습자는 어떤 기술을 배워야 하는지 몰라서 인기 강의를 따라가고, 기업 수요 데이터는 채용공고, 고용24, AI Hub처럼 여기저기 흩어져 있습니다. 운영하는 쪽도 추천이 실제로 수강으로 이어지는지 숫자로 보기 어렵습니다. 그래서 저희는 수요를 분석하고, 내 역량을 진단하고, 그 사이의 갭을 계산해 강의를 추천하고, 그 성과를 다시 운영 지표로 돌려보는 하나의 순환 구조로 풀었습니다.

**면접관 어필 포인트**: 기능이 아니라 '문제 정의 → 순환 구조'로 시작하는 기획력

## 3. 솔루션: 세 가지 핵심 기능 + 운영 시스템  _(3:00 누적 · 70초)_

**핵심 시각 자료**: 3열 카드(01 수요 분석 / 02 AI 진단 / 03 맞춤 Pick) + 하단 운영 띠

**본문**

- 01 기업 수요 분석: 직무·산업·지역 필터, 워드클라우드, 12개월 시계열, 기업 수요 등록→AI 구조화
- 02 AI 역량 진단: 직무별 문항, 역량 레이더, 기업 요구 대비 Gap
- 03 맞춤 학습 Pick: 매칭률, 3단계 로드맵, AI 튜터(스트리밍·출처 표기)
- 운영: 회원·권한, 콘텐츠·태그, 모니터링 대시보드

**발표자 스크립트**

> 핵심 기능은 세 가지입니다. 첫째, 기업 수요 분석입니다. 직무, 산업, 지역으로 걸러서 어떤 역량이 뜨고 있는지 보고, 기업 담당자가 채용 요건을 글로 쓰면 AI가 필수와 우대로 구조화합니다. 둘째, AI 역량 진단입니다. 결과는 레이더 차트와 기업 요구 수준 대비 갭으로 보여드립니다. 셋째, 갭을 가장 효율적으로 줄이는 강의와 3단계 로드맵을 추천하는 맞춤 Pick입니다. 그리고 이 모든 것을 운영하는 관리자 시스템까지 하나의 플랫폼으로 묶었습니다.

**면접관 어필 포인트**: B2C(학습자) + B2B(기업) + 운영(관리자) 3축을 한 제품으로 설계

## 4. 전체 시스템 아키텍처  _(4:30 누적 · 90초)_

**핵심 시각 자료**: 좌→우 3단 구성도: Client / API / Data·외부 서비스 + 하단 CI/CD 흐름

**본문**

- Client: React 19 + Vite + Tailwind v4 (Netlify 데모 · Render Static)
- API: FastAPI (Docker, Render Web Service) — Auth/Demand/Diagnosis·Recommend/Tutor(SSE)/Admin
- Data: TiDB Cloud(MySQL 호환, TLS) · 로컬·테스트는 SQLite 폴백
- External: Gemini(선택, 규칙 기반 폴백) · OAuth(Google/Naver/Kakao)
- CI/CD: GitHub Actions → 경로 감지 → 테스트·빌드 → Render REST API

**발표자 스크립트**

> 전체 구조입니다. 왼쪽 프런트는 React와 Tailwind로 만들어 Netlify와 Render 정적 사이트에 올렸고, 가운데 API는 FastAPI를 Docker로 말아 Render 웹 서비스로 돌립니다. 데이터는 TiDB 클라우드를 쓰되 로컬과 테스트에서는 SQLite로 자동 전환됩니다. Gemini는 키가 있으면 호출하고 없으면 규칙 기반으로 대체해서, 외부 서비스가 없어도 서비스는 항상 뜨도록 했습니다. 아래쪽은 GitHub Actions가 변경된 영역만 검증하고 배포하는 흐름이고, 점선으로 표시한 수집 파이프라인은 담당자 이오리 님이 설계한 확장 영역입니다.

**면접관 어필 포인트**: 프런트/백엔드 분리 배포, 외부 의존성 격리(폴백) 설계

## 5. 기술 선택의 근거 (Why)  _(5:45 누적 · 75초)_

**핵심 시각 자료**: 표: 선택 / 이유 / 포기한 것(트레이드오프)

**본문**

- FastAPI: Pydantic 검증 + Depends 기반 RBAC + 자동 OpenAPI
- TiDB + SQLite 폴백: 운영은 MySQL 호환 클라우드, 테스트는 격리된 임시 DB
- 직접 구현한 SVG 차트: 라이브러리 0개, 번들 gzip 146KB, Gap Bridge 같은 도메인 시각화
- Gemini + 규칙 기반 폴백: 키·비용·장애와 무관하게 데모 동작
- Render REST API 배포: Deploy Hook 대신 상태 폴링·로그 수집

**발표자 스크립트**

> 기술은 유행이 아니라 이유로 골랐습니다. FastAPI는 요청 검증과 권한 검사를 의존성 주입으로 깔끔하게 걸 수 있어서 선택했습니다. 데이터베이스는 운영에서는 MySQL 호환 TiDB, 테스트에서는 임시 SQLite로 격리해 같은 SQL로 둘 다 돌립니다. 차트는 라이브러리를 쓰지 않고 SVG로 직접 만들어서 번들을 줄이고, 기업 요구 대비 갭 같은 저희 도메인에 맞는 시각화를 만들 수 있었습니다. AI도 키가 없으면 규칙 기반으로 내려가게 해서 장애가 서비스 전체로 번지지 않게 했습니다.

**면접관 어필 포인트**: '무엇을 썼나'가 아니라 '무엇을 포기하고 무엇을 얻었나'를 말하는 의사결정 근거

## 6. 핵심 기술 ①  수요 데이터 파이프라인  _(7:15 누적 · 90초)_

**핵심 시각 자료**: 5단계 흐름(수집→정제→분석→적재→서비스) + 구현 현황 표(현재/로드맵)

**본문**

- 수집: Requests·BS4·Playwright, 공공데이터포털·고용24·AI Hub
- 정제: pandas·NumPy (중복·결측·표준화)
- 분석: 형태소 분석 → 역량 사전 18종(별칭 매핑) 키워드 추출
- 적재: demand_stats(월×직무×산업×지역×역량) 6,912행
- 서비스: 최근 3개월 vs 직전 3개월 급상승률, 직무별 요구 수준 정규화
- 현재 구현: 규칙 기반 추출·집계 API·시계열 데이터 모델 / 로드맵: 실수집 크롤러·스케줄러

**발표자 스크립트**

> 수요 분석의 뼈대는 이 다섯 단계 파이프라인입니다. 채용공고와 공공 데이터를 모으고, pandas로 정제하고, 형태소 분석 결과를 역량 사전에 매핑해 키워드를 뽑아, 월·직무·산업·지역·역량 단위로 TiDB에 쌓습니다. 서비스 단에서는 최근 석 달과 직전 석 달을 비교해 급상승 역량을 계산하고, 직무별 요구 수준도 이 빈도로 정규화합니다. 솔직하게 말씀드리면, 지금 배포본의 수치는 공공 데이터의 분포를 모사한 시드 데이터이고 실제 크롤러와 스케줄러는 다음 단계입니다. 대신 수집 결과가 들어오면 바로 붙을 데이터 모델과 집계 API는 완성되어 있습니다.

**면접관 어필 포인트**: 구현 범위와 로드맵을 정직하게 구분 — 데이터 모델·집계 로직은 실제 동작

## 7. 핵심 기술 ②  갭 분석과 추천 알고리즘  _(8:45 누적 · 90초)_

**핵심 시각 자료**: 좌: 수식 박스 5개 / 우: 진단 결과 화면(레이더 + Gap Bridge)

**본문**

- 점수 = 정답 60 + 자신감×8  (최대 100)
- 요구 수준 = 55 + 40 × (최근 3개월 빈도 ÷ 직무 내 최대 빈도)
- 갭 = max(0, 요구 − 점수) · 준비도 = Σmin(점수,요구) ÷ Σ요구
- 강의 점수 = Σ(커버하는 갭) × 난이도 보정 ÷ (1 + 시간/40)
- 매칭률 = 60 + 39 × 강의 점수 ÷ 최고 점수 → 3단계 로드맵 배치

**발표자 스크립트**

> 분석 로직은 설명 가능하게 만들었습니다. 진단 점수는 정답 여부 60점에 자신감 점수를 더하고, 기업 요구 수준은 최근 석 달 공고 빈도를 직무 안에서 정규화해 55에서 95 사이로 둡니다. 둘의 차이가 갭이고, 강의는 자신이 메워주는 갭의 합을 학습 시간으로 나눠 점수화합니다. 그래서 같은 효과라면 짧고 쉬운 강의가 먼저 추천됩니다. 이 결과를 레이더와 갭 브릿지로 시각화했는데, 검은 눈금이 기업 요구, 사선 구간이 채워야 할 부분입니다. 블랙박스 모델이 아니라서 왜 이 강의가 추천됐는지 화면에서 바로 설명됩니다.

**면접관 어필 포인트**: 수식 단위의 설명 가능성(Explainability) + 도메인 특화 시각화

## 8. 인증·보안과 로그인 UX  _(9:55 누적 · 70초)_

**핵심 시각 자료**: 좌: 로그인 화면 캡처 / 우: 보안 체크리스트

**본문**

- Split 레이아웃, 소셜 3사(카카오·네이버·Google) 브랜드 가이드 버튼 + '최근 사용'
- 비밀번호 정규식(영문 대·소문자+숫자+특수문자 8자↑) 프런트·서버 동일 검증
- 테스트 계정 3종(학습자·기업·테스트 관리자) — 클릭 시 자동 입력 후 로그인
- JWT(HS256, 12h), PBKDF2-SHA256 310,000회 해시
- 실제 관리자: ADMIN_SECRET_KEY를 서버에서 hmac.compare_digest로 검증(VITE_ 금지)

**발표자 스크립트**

> 로그인은 면접관님도 바로 체험하실 수 있게 설계했습니다. 소셜 로그인 버튼은 카카오, 네이버, 구글 각 사의 브랜드 가이드를 따랐고 마지막에 쓴 방식에는 최근 사용 표시가 붙습니다. 그 아래 테스트 계정 버튼을 누르면 자동으로 입력되고 로그인됩니다. 보안 쪽에서는 비밀번호 규칙을 프런트와 서버가 똑같이 검증하고, 해시는 PBKDF2 31만 회, 토큰은 JWT를 씁니다. 실제 관리자는 서버 환경 변수의 비밀 키로만 들어올 수 있고, 이 키는 프런트 코드에 절대 노출되지 않도록 분리했습니다.

**면접관 어필 포인트**: 사용성(원클릭 체험)과 보안(서버 검증·키 분리)의 균형

## 9. 핵심 유저 플로우: 진단에서 Pick까지  _(11:15 누적 · 80초)_

**핵심 시각 자료**: 상단 6단계 칩 + 하단 두 화면(진단 결과 / 맞춤 Pick)

**본문**

- 직무 선택 → 역량별 문항 + 자신감 → 레이더·갭 → Pick(매칭·로드맵) → 수강·진도 → 마이페이지 리포트
- 진단 결과는 DB에 저장되어 Pick·메인·마이페이지가 같은 데이터를 공유
- 스켈레톤·빈 상태·에러 상태를 모든 데이터 영역에 동일 컴포넌트로 적용

**발표자 스크립트**

**발표자 스크립트**

**면접관 어필 포인트**: 1인이 아닌 팀 협업에서도 유지되는 토큰 기반 디자인 시스템

## 11. 관리자 백오피스와 권한 제어(RBAC)  _(13:35 누적 · 70초)_

**핵심 시각 자료**: 좌: 테스트 관리자 화면(읽기 전용 배지) / 우: 권한×기능 표 + 3중 방어선

**본문**

- 학습자·기업 담당자·실제 관리자(admin)·테스트 관리자(admin_readonly) 4개 권한
- admin: 회원·권한, 강의, 역량 태그, 공지 전체 CRUD
- admin_readonly: 모든 화면 조회 가능, 변경 요청은 403 (읽기 전용 배지·툴팁·토스트)
- 방어선 ① UI(WriteButton·배지) ② 라우트 가드 ProtectedRoute ③ 서버 미들웨어 + Depends(require_admin)

**발표자 스크립트**

> 관리자 영역은 권한을 네 단계로 나눴습니다. 실제 관리자는 회원 권한 변경, 강의와 태그, 공지까지 전부 수정할 수 있고, 테스트 관리자는 화면은 똑같이 보지만 읽기 전용입니다. 중요한 점은 프런트만 믿지 않는다는 것입니다. 버튼을 비활성화하는 것은 보조 수단이고, 최종 방어는 서버 미들웨어가 테스트 관리자의 POST, PUT, PATCH, DELETE를 모두 403으로 막는 것입니다. 이 동작은 자동 테스트로 고정해 두어서 권한이 우회되는 회귀를 막고 있습니다.

**면접관 어필 포인트**: UI 제어 ≠ 보안 — 서버 최종 검증과 회귀 테스트

## 12. DevOps: GitHub Actions 조건부 배포  _(14:55 누적 · 80초)_

**핵심 시각 자료**: 파이프라인 다이어그램(push→경로 감지→테스트/빌드→Render API→헬스체크) + 시크릿 위치 표

**본문**

**발표자 스크립트**

**면접관 어필 포인트**: 변경 감지·검증 게이트·관측 가능성(로그)을 갖춘 실무형 파이프라인

## 13. 트러블슈팅: 실제로 부딪힌 문제 3가지  _(16:45 누적 · 110초)_

**핵심 시각 자료**: 3열 카드(증상 / 원인 / 해결 / 결과) + 보너스 한 줄

**본문**

- ① Render build_failed — 'open Dockerfile: no such file' → 서비스 Root Directory(backend) ≠ 저장소 루트 Dockerfile → 배포 스크립트가 서비스 설정을 조회·교정(PATCH), 실패 로그 자동 출력
- ② 컨테이너 기동 직후 종료 — DATABASE_URL이 .env.example의 USER:PASS@HOST 예시값 → pymysql 2003 → 플레이스홀더 감지 시 경고 + SQLite 폴백, 배포 전 사전 경고
- ③ 테스트 관리자 우회 가능성 — UI만 막으면 API 직접 호출로 변경 가능 → 미들웨어 403 + 튜터 질의만 예외, 회귀 테스트로 고정
- 보너스: 무료 서버 콜드 스타트 → 스켈레톤 + 4초 후 안내 + 60초 응답 캐시

**발표자 스크립트**

> 가장 말씀드리고 싶은 부분입니다. 첫 번째, Render 배포가 build failed로 떨어졌습니다. 로그를 보니 도커 파일을 찾을 수 없다는 메시지였고, 서비스의 루트 디렉터리가 backend로 잡혀 있었는데 도커 파일은 저장소 루트에 있었습니다. 그래서 배포 스크립트가 서비스 설정을 읽어 어긋나면 API로 교정하고, 실패 시 로그를 자동 출력하게 만들었습니다. 두 번째, 빌드는 됐는데 컨테이너가 바로 죽었습니다. 환경 변수에 예시용 DB 주소가 그대로 들어 있었던 겁니다. 플레이스홀더를 감지해 경고하고 SQLite로 내려가게 해서 서비스가 먼저 살아나도록 했습니다. 세 번째, 읽기 전용 관리자를 화면에서만 막으면 API 직접 호출로 뚫린다는 점을 발견해 서버 미들웨어로 막고 테스트로 고정했습니다.

**면접관 어필 포인트**: 증상→원인→해결→재발 방지(자동화·테스트)까지 이어지는 문제 해결 서사
